# Excavator Path Planning Analysis

Date: 2026-07-09

Current-status note (audited 2026-07-15): the shared validators and the dig vs
loaded-unload split described below still exist. The candidate-selection layer
has since gained `rank_dig_plan_candidates_cheap()` and `cheap_rank_v1`.
`build_dig_plan_from_current_target()` now cheaply ranks all adaptive
candidates, fully plans the primary Top-K window (default 3), compares complete
plans with expert cost, and then uses qualified staged-prefix or progressive
fallback selection. `PLAN_BUILD_SUMMARY` records this selection scope. Older
line numbers and statements that imply every candidate receives full planning
should be treated as historical. See `current_runtime_architecture.md` for the
current top-level chain.

This note summarizes the current path planning implementation in
`scripts/excavator_app/excavator_runtime.py` for expert review. The main
question is whether "reach to dip sand" and "unload to truck" use the same
planner, and where the core planning logic lives.

## Short Answer

`reach to dip sand` and `unload to truck` do **not** use exactly the same
top-level planning function.

They do share the same lower-level path validation stack:

- `path_segment_check()`
- `path_phase_check()`
- `path_obstacle_check()`
- `find_clearance_route()`
- `route_segments_ok()`
- optional `joint_space_planner.plan_joint_space_route()`

But their higher-level logic is different:

- Dig / reach-to-sand stages are generated by `dig_plan_specs_from_candidate()`
  and solved by `plan_dig_sequence_candidate()`.
- Truck unload is partly represented as a normal stage in the initial candidate
  plan, but the real loaded unload route is usually appended later after
  `secure_load` by `append_staged_post_secure_load_plan()`.

So the current system is a hybrid:

```text
candidate dig planner
  -> IK per stage
  -> direct path precheck
  -> optional clearance route
  -> staged runtime append for secure/load/unload
```

It is not a single global trajectory optimizer.

## Current Planner Entry Points

### Main build entry

```python
build_dig_plan_from_current_target()
```

Responsibilities:

- Reads current target position.
- Gets or reuses a planning sand snapshot.
- Validates the target.
- Clears previous plan state.
- Calls `plan_dig_sequence_from_target()`.
- Stores:
  - `STATE["dig_plan_sequence"]`
  - `STATE["dig_plan_points"]`
  - `STATE["current_dig_plan"]`
  - `STATE["dig_plan_candidate"]`

### Candidate-level planner

```python
plan_dig_sequence_from_target(target_xyz, max_seconds=None)
```

Responsibilities:

- Calls `adaptive_dig_plan_candidates(target_xyz)`.
- Evaluates candidate dig primitives until a valid or early-accepted plan is
  found.
- Uses `plan_dig_sequence_candidate()` for each candidate.
- Tracks `PLAN_BUILD_SUMMARY`.

### Stage-level candidate planner

```python
plan_dig_sequence_candidate(target_xyz, candidate, deadline=None)
```

This is the core high-level planner for the dig chain. It first converts a dig
candidate into stage specs:

```python
dig_plan_specs_from_candidate(target_xyz, candidate)
```

Current generated stages:

```text
pre_dig
approach_contact
insert_cut
pull_mid_cut
curl_to_hold_material
pull_exit_cut
secure_load
lift_carry
unload_to_bin
```

Important detail: the stages are not all equivalent. The early dig phases solve
for the bucket tip or load point relative to the sand. The unload stage calls
the dump-specific logic.

## Reach-To-Dip-Sand Planning Chain

For stages such as `pre_dig`, `approach_contact`, `insert_cut`,
`pull_mid_cut`, `curl_to_hold_material`, and `pull_exit_cut`, the chain is
approximately:

```text
target point
  -> adaptive_dig_plan_candidates()
  -> dig_plan_specs_from_candidate()
  -> solve_dig_pose_candidates()
  -> solve_priority_ik_to_target()
  -> routed_stage_components()
  -> path_phase_check()
  -> path_obstacle_check()
  -> optional find_clearance_route()
```

The dig stage specs include:

- desired world point
- target bucket joint angle or bucket world angle
- IK effector: usually `tip` for entry, `load` for load/carry phases
- duration
- whether the stage is required

Important current behavior:

- `pre_dig` may request a clearance route if the direct corridor intersects
  a rigid obstacle.
- Most non-obstacle dig phases prefer direct IK-to-IK motion.
- Cutting/curl phases have looser ground/body handling than travel/carry
  phases, because the bucket is expected to enter sand.

## Unload-To-Truck Planning Chain

Unload planning has two layers.

### 1. Initial candidate unload stage

Inside `plan_dig_sequence_candidate()`, when the stage label is
`unload_to_bin`, the planner calls:

```python
plan_dump_pose_to_bin()
```

This solves a release / dump pose based on:

- current carry pose seed
- truck/unload mesh landing point
- desired release point
- predicted drop model
- bucket opening / pour point
- dump angle
- optional best-effort IK

This is not the same as the sand approach solver. It uses the same underlying
IK primitive, but with `end_effector="pour"` and dump/drop-specific scoring.

### 2. Staged post-secure unload append

The more important runtime path is:

```python
append_staged_post_secure_load_plan()
```

This runs after material has actually been secured/lifted. It starts from the
current actual pose instead of only relying on the original planned pose.

The core steps are:

```text
current q after secure/lift
  -> plan_dump_pose_to_bin()
  -> compute_pre_dump_carry_pose()
  -> validate_unload_goal()
  -> path_segment_check(q_lift, q_pre_dump, "unload_to_bin")
  -> loaded_carry_path_height_check()
  -> if direct blocked: find_clearance_route(..., mode="unload_to_bin")
  -> if route blocked: staged_high_carry_unload_fallback()
  -> append clearance_route_post_N stages
  -> append final unload_to_bin stage
```

This is the truck route planner most relevant to current unload failures.

## Shared Low-Level Path Validation

### `path_segment_check(q_start, q_goal, mode, samples, deadline)`

This is the common gate used by both dig approach and unload route planning.
It checks:

1. Phase / ground safety:

```python
path_phase_check()
```

2. Rigid obstacle sweep:

```python
path_obstacle_check()
```

If either fails, the segment is rejected.

### `path_phase_check()`

Interpolates from `q_start` to `q_goal` and evaluates predicted phase/ground
reports at each sample.

This is where failures like:

```text
tip too deep
body below clearance
bucket body still too deep
ground/path guard violation
```

can originate.

### `path_obstacle_check()`

Interpolates from `q_start` to `q_goal` and checks predicted robot link
segments against rigid obstacle proxies.

Current obstacle representation:

- rigid obstacle bboxes
- optional mesh footprint prism proxy
- link segment sweep approximation
- margins:
  - `PATH_OBSTACLE_MARGIN_XY`
  - `PATH_OBSTACLE_MARGIN_Z`
  - `PATH_LINK_COLLISION_RADIUS_M`

This is where failures like:

```text
predicted rigid link sweep contact
```

come from.

### `find_clearance_route()`

Used when direct path is blocked or route is preferred.

It generates route candidates using:

- deterministic joint tuck / swing poses
- swing detours
- high approach variants
- optional joint-space RRT fallback via `joint_space_planner.py`

For loaded/carry/unload modes it may force bucket carry geometry:

```python
mode_requires_loaded_carry_bucket()
force_loaded_carry_bucket_q()
```

This means unload routing is more constrained than empty-bucket pre-dig routing.

## Is The Current Planner Potentially Problematic?

Yes. The current structure works, but it has several likely weak points.

### 1. It is stage-wise, not globally optimized

The planner solves one stage after another. Each stage chooses a target pose and
then checks the segment. This can create locally valid but globally awkward
motions.

Example:

```text
pre_dig ok
approach_contact ok
insert_cut ok
pull_mid_cut ok
secure ok
then unload route becomes hard or blocked
```

The planner does not search a single continuous trajectory from start to dump
with one objective.

### 2. Dig and unload share collision checks, but not semantics

Sharing `path_segment_check()` is useful, but the same checker is used for very
different tasks:

- empty-bucket travel to sand
- bucket entering deformable sand
- loaded carry
- truck approach
- dump alignment

Those phases have different acceptable contact/clearance rules. The code tries
to distinguish them by `mode`, but this creates many special cases and makes
debugging hard.

### 3. Rigid obstacle approximation can be too conservative or misaligned

`path_obstacle_check()` uses link segment sweeps against bbox / footprint prism
proxies. This is fast, but for a rotated truck dump bed it may reject paths that
are actually physically valid, or accept paths with poor margin depending on
proxy quality.

This matters most for:

```text
unload_to_bin
clearance_route_post_N
staged_unload_to_bin
```

### 4. Loaded carry route has extra constraints

Unload route planning can force bucket carry posture and height floors:

```text
force_loaded_carry_bucket_q()
loaded_carry_path_height_check()
loaded_carry_route_height_check()
```

This prevents spilling but can overconstrain route search. If the carry geometry
projection changes the bucket or arm enough, candidate routes may fail even
when a smoother coordinated route exists.

### 5. `find_clearance_route()` is still mainly candidate based

The route search first tries deterministic poses and detours. RRT exists, but
it is a fallback and still uses the same edge checker. This can miss routes that
need coordinated boom/arm/swing motion rather than a tuck-then-swing template.

### 6. Planning and execution are not fully unified

The staged planner appends unload after secure/lift using actual q. This is good
and was added to avoid using stale pre-load assumptions. But it also means the
initial "full plan" and runtime staged append are two different planning
moments.

This can make diagnostics confusing:

- initial candidate says unload planned
- secure/lift changes actual q
- staged append recomputes route
- final route may differ from initial plan

## Suggested Expert Review Questions

1. Should unload route planning use a dedicated truck-local planner instead of
   the generic `find_clearance_route()`?

2. Should obstacle collision use a tighter OBB / mesh-SDF / capsule model rather
   than bbox / footprint prism proxies for truck and dump bed?

3. Should loaded carry planning be formulated as constrained trajectory
   retiming/optimization instead of forcing carry posture at each candidate q?

4. Should dig approach and loaded unload have separate edge validators rather
   than sharing one `path_segment_check()` with many mode branches?

5. Should the planner search in task space first for unload:

```text
bucket load point / pour point path
  -> constrained IK along path
  -> joint-space smoothing
```

instead of:

```text
joint pose candidates
  -> link sweep check
  -> fallback route
```

6. Should the initial plan stop before unload and always run staged post-secure
   unload planning from actual loaded q? That may simplify the contract and make
   diagnostics clearer.

## Practical Current Interpretation

When analyzing logs:

- `planning_failed/staged_unload_dump_pose:*` usually comes from
  `plan_dump_pose_to_bin()`.
- `planning_failed/staged_unload_goal:*` usually comes from
  `validate_unload_goal()`.
- `planning_failed/staged_unload_route:*` usually means direct unload path was
  blocked and `find_clearance_route()` plus fallback failed.
- `execution_failed/path_precheck_failed:unload_to_bin:*` usually means runtime
  execution precheck called `path_segment_check()` and got a phase/obstacle
  failure.
- `predicted rigid link sweep contact` comes from `path_obstacle_check()`.
- `loaded_carry_height_drop` comes from loaded carry height floor checks after
  secure/lift.

## Bottom Line

The current planner is a layered, stage-wise IK planner with shared segment
validation and candidate-based clearance routing. It is not a unified motion
planner.

`reach to dip sand` and `unload to truck` share collision/path-check machinery,
but the unload path has extra staged logic, drop prediction, carry pose
projection, height-floor checks, and route fallback. Most current unload
failures should therefore be analyzed in `append_staged_post_secure_load_plan()`,
`plan_dump_pose_to_bin()`, `path_segment_check()`, and `find_clearance_route()`.

## V1 Changes Applied

The first implementation pass follows the P0 recommendations without replacing
the whole planner.

Implemented:

- Added `EXCAVATOR_EXPERT_PLANNER_V1`, enabled by default.
- Planner version now reports `dig_plan_v4_joint_space_world_debug_expert_v1`
  when V1 is active.
- Auto collect no longer returns immediately on the first valid target plan.
  It now collects successful plans within the same target ring and selects the
  lowest-cost success.
- Added V1 planning defaults:
  - `AUTO_DIG_FULL_PLAN_TOPK_PER_RING`: 8
  - `AUTO_COLLECT_MAX_FULL_PLAN_ATTEMPTS`: 12
  - `AUTO_COLLECT_FIND_PLAN_MAX_SECONDS`: 60s
  - `AUTO_COLLECT_CANDIDATE_PLAN_SECONDS`: 12s
  - `AUTO_COLLECT_MIN_SUCCESS_PER_RING`: 3
  - `AUTO_COLLECT_CONTINUE_AFTER_FIRST_SUCCESS_SECONDS`: 4s
- Disabled normal and staged-prefix early accept by default in V1.
- Added expert rank cost:
  - base planner cost remains the dominant term
  - legacy candidate quality score can improve rank
  - path warnings, unload warnings, carry warnings increase rank cost
  - simple dig fill-potential proxy can improve rank
- `auto_dataset_collect.find_plan()` now uses the selected candidate
  `rank_cost` instead of only the shared plan's raw motion cost.
- `joint_space_planner.py` RRT seed is now stable SHA-256 based on label, mode,
  quantized start/goal q, episode seed, and obstacle cache version. It no
  longer uses Python `hash()` or `time.time()`.

Not implemented in V1:

- Full `PathModePolicy` replacement for string modes.
- Dynamic obstacle time verifier.
- Dedicated `TruckUnloadPlanner` with top-K landing / release / route joint
  search.
- Loaded carry hard projection plus soft envelope dual-route scoring.
- LazyPRM/SIPP/BIT*/CEM planner backends.

V1 can be disabled for comparison:

```powershell
$env:EXCAVATOR_EXPERT_PLANNER_V1="0"
```
