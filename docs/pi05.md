# Excavator PI05 pipeline

## Scope and status

The initial baseline is **PI05 expert-only fine-tuning**, not full-model tuning
or LoRA. The frozen VLM remains in the immutable `models/pi05_base` asset. The
action expert, action projections and time conditioning are fine-tuned. The
unused expert causal-LM output head is frozen as well.

Current training uses **FP32 trainable storage with BF16 autocast**, not an
all-FP32 model. `training.trainable_dtype: float32` keeps expert, action/time
projections, gradients and AdamW moments in FP32. `policy.dtype: bfloat16`
initializes the frozen backbone using upstream mixed BF16/FP32 rules. Trainable
parameters are widened **before** strict loading of the original FP32 base,
so pretrained precision is not discarded by a BF16 load followed by widening.
New-checkpoint inference automatically enters the same BF16 CUDA autocast as
training, including offline evaluation and Isaac. CPU checks use FP32 without
autocast. No upstream LeRobot or immutable base files are modified.

Implementation includes strict base/delta loading, train-only quantiles,
weighted/masked flow matching, deterministic batch addressing, resume, offline
metrics, and an entrypoint into the shared Isaac evaluator. Implementation and
unit-test success must not be presented as real-model training or task success.
Record each real GPU experiment separately.

## VLM LoRA + full expert experiment

The optional `training.mode: vlm_lora_expert_full` adapts only the VLM Gemma's
q/k/v/o attention projections (r=16, alpha=32, dropout=0); SigLIP and base VLM
weights stay frozen. The action expert and action/time projections remain full
FP32. Adapters also retain FP32 storage/moments, with BF16 CUDA forward compute.
The native `LoRALinear` keeps upstream `.weight`/`.bias` and state-key behavior;
no upstream source, installed Transformers, or pretrained asset is rewritten.

Base loading is strict and happens before injection; inference reconstructs the
same target modules from `checkpoint.json` before restoring the trained delta.
The saved delta includes expert plus LoRA weights, never another base copy.
Adapters are not merged into BF16 base weights. Legacy expert-only manifests
remain supported; exact resume cannot change mode, rank, targets or dropout.

New runs check zero-adapter equivalence on an actual recorded observation and
fixed sampling seed, then audit the first update. `zero_lora_check.json` and
`first_update_check_000001.json` distinguish these numerical gates from learning.
LoRA A may legitimately have zero first-step gradient while zero-initialized B
receives an update. Dedicated initialization generators preserve training RNG.

```bash
# Run the Environment setup below first; commands are from the parent checkout.

"$PI05_PYTHON" ExcavatorVLA-vlm/scripts/train_pi05.py \
```

is synchronized per update. Peak memory and throughput must be measured, not
assumed to improve by exactly 2x. The smoke uses accumulation 1/batch 2 only as
an integration check, not an A/B performance point.

`scripts/run_pi05_lora_ab.py` can own the complete bounded experiment. It requires
completed current-simulator expert/replan-1/replan-3 gates, then verifies smoke
and independent reload, runs the two matched dual-GPU training arms sequentially,
evaluates the entire training Episode 1 on separate GPUs concurrently, and
records matched reference-scene videos. It pins relevant runtime source hashes,
refuses overwrite, waits for idle GPUs and stops on errors/source drift/low disk.
Inspect its `status.json`, `logs/` and final `comparison.json`. It does not
automatically launch the 5k pilot or 40k full training; one-episode findings are
not held-out benchmark success. Old 10-batch validation logs are still held-out
diagnostics: only the explicit `--split train --episodes 1` evaluation measures
training-episode fitting.

## Input/output contract

- Input: the same three `observation.images.0/1/2` RGB cameras, source 256x256,
  floating-point [0,1], plus 28D current-v4 state and the recorded task string.
- Image resizing to 224x224 and conversion to [-1,1] happen inside PI05. Do not
  apply ACT ImageNet normalization or normalize an image twice.
- State: train-only q01/q99 normalization, internal padding to 32D, then official
  discrete-state prompt preparation. Tokens must fit without silent truncation.
- Action: the existing four command velocities in rad/s, ordered swing/boom/arm/
  bucket. Normalize four real dimensions, pad internally to 32, return four real
  dimensions, and unnormalize before physical clipping/execution.
- No position differencing, relative-action conversion, or categorical phase/
  effort inputs. The state retains the same simulator-derived target/fill
  information as ACT, so this is an instrumented-state benchmark.
- Predict 10 actions at 10 Hz and execute 3 before replanning. This deliberately
  differs from the base checkpoint's native 50/50 setting and is recorded as a
  benchmark adaptation. RTC and compilation are disabled initially.

The split stays at 160 train / 20 validation / 20 test episodes. Quantiles use
only the actual training subset, including for one-episode overfit. The raw
dataset/global statistics are not modified. Temporal padding and zero-weight
targets do not contribute to flow matching. Only the four real action channels
are supervised. Loss normalization uses the total valid weight across all
micro-batches and ranks, rather than an average of differently sized means.

## Checkpoints and interruption/resume

```text
outputs/train/<run>/
  resolved_settings.json, training_config.yaml
  dataset_contract.json, split_manifest.json, normalization_stats.json
  provenance.json, train.log, validation_history.jsonl
  last_checkpoint.json, best_checkpoint.json, reload_check.json
  checkpoints/000020/
    training_state.pt
    validation.json
    pretrained_model/
      config.json, checkpoint.json
      model.safetensors            # trainable delta, NOT a full model
      normalization_stats.json, benchmark_provenance.json
      policy_preprocessor.json, policy_postprocessor.json
      processor state files
```

The delta manifest pins the base and the exact trained key set. The loader
strictly verifies base checksum, delta checksum, keys and shapes; it never uses
the upstream PI05 loader's silent random/partial fallback. **Delta files must not
be loaded as full models using stock `PI05Policy.from_pretrained`.** Use the
project's `load_pi05` or the supplied CLIs. The base is not copied into every
checkpoint. This is a base-referencing checkpoint, not a standalone export.

`last_checkpoint.json` and `best_checkpoint.json` are regular JSON pointers,
not symlinks. The retention policy keeps the most recent configured number plus
any best/last protected checkpoint, pruning only complete owned PI05 checkpoints
inside that experiment. It never prunes ACT checkpoints or pretrained assets.
Validation metrics are also appended to `validation_history.jsonl`, so pruning
weight files does not discard the learning curve.

To test interruption without changing the planned schedule:

```bash
"$PI05_PYTHON" ExcavatorVLA-vlm/scripts/train_pi05.py \
  --config ExcavatorVLA-vlm/configs/pi05/smoke.yaml --gpus 1 \
  --steps 2 --stop-after 1 --output "$BASE/outputs/train/pi05_resume_check"

"$PI05_PYTHON" ExcavatorVLA-vlm/scripts/train_pi05.py \
  --config ExcavatorVLA-vlm/configs/pi05/smoke.yaml --gpus 1 \
  --steps 2 --resume "$BASE/outputs/train/pi05_resume_check"
```

Resume restores optimizer, scheduler, RNG and consumed-batch addressing. It
requires the latest checkpoint, original run directory, same data/split/stats,
same policy settings, and unchanged world size/micro-batch/accumulation. Schedule
timings are restored, not silently restarted. Extending the target steps beyond
the original schedule does not invent a new learning-rate schedule. The sampler
is addressed by consumed batches, not DataLoader prefetch progress. This exact
data-addressing guarantee assumes the current deterministic, unaugmented dataset.

### Explicit learning-rate-changing continuation

By default, `--resume` retains the saved schedule, including its floor after
the original decay budget. `--resume-lr 2.5e-5` is a deliberate exception: it
keeps optimizer moments/counters, RNG and consumed-data progress, but replaces
the remaining schedule with a constant 2.5e-5, without warmup. This is **not**
an exact continuation of the original optimization trajectory. The override
is recorded in the resume settings, saved schedule and actual train-log LR.
Resuming that new checkpoint without another override preserves its new
constant schedule. The original PI05 model configuration is not rewritten to
fake a schedule restart.

The bounded continuation runner accepts `--resume-parent <completed-A/B>` and
`--extra-steps 1000 --resume-lr 2.5e-5`. It continues both existing training
runs in place with two GPUs and effective batch 8, preserves earlier checkpoint
directories via the continuation configs' retention setting, and writes new
offline results/videos/comparisons under a **new** `--output` directory.
Do not start another continuation of the same runs concurrently. Runtime files
and configs are pinned while the job runs; unrelated RL edits are not part of
that pin.

The current requested continuation is
`outputs/experiments/pi05_lora_ab_continue3000_20261028_01/`: both arms go from
2,000 to 3,000 updates at fixed LR 2.5e-5. The original 2k comparison and videos
remain under `outputs/experiments/pi05_lora_ab_20261028_01/`. User-approved GPU
sharing is enabled for this continuation; each stage still requires at least
20 GiB free on both selected GPUs and never terminates other processes.
Read `status.json`, the sibling `.launcher.log` and `logs/` for live state.
New `comparison.json` and `step_comparison.json` are written only after the
continued models are evaluated; no performance improvement is assumed.

New manifests record `precision_contract: fp32_trainable_bf16_autocast_v1` and
actual trainable/frozen dtype counts. Older checkpoints without this field keep
their original inference precision for reproducible comparisons. They are
deliberately rejected by exact resume into FP32 training: historical rounding,
optimizer state and forward precision cannot be made equivalent after the fact.
For the precision comparison below, start a new run from the immutable base;
do not resume the old 2,000-step BF16 run or restart its exhausted schedule.

For checkpoint relocation, override immutable asset locations using
`EXCAVATOR_PI05_BASE` / `EXCAVATOR_PI05_TOKENIZER`; the base checksum must still
match. Do not edit the base asset's original config/weights.

## Offline evaluation and Isaac

`--checkpoint` accepts a run directory (latest), a step directory, or its
`pretrained_model` directory. Replace the example paths with the actual run.

```bash
export PI05_CHECKPOINT="$BASE/outputs/train/<actual-pi05-run>"
"$PI05_PYTHON" ExcavatorVLA-vlm/scripts/eval_pi05_offline.py \
  --checkpoint "$PI05_CHECKPOINT" --split validation --batch-size 1 \
  --output "$BASE/outputs/eval/pi05_validation_<unique-name>"

"$PI05_PYTHON" ExcavatorVLA-vlm/scripts/eval_pi05_success.py \
  --checkpoint "$PI05_CHECKPOINT" --dataset "$BASE/data/export" \
  --output "$BASE/outputs/eval/pi05_seed2_<unique-name>" \
  --episodes 1 --steps 350 --initial-episode 1 --seed 2 \
  --min-particles 100 --replan-interval 3 --gpus 1 --workers 1 --video
```

Offline metrics use physical-unit actions at recorded observations, not simulated
success. The evaluator passes language tasks for PI05 and keeps ACT inputs
unchanged. Inference is stochastic; validation/reload checks use fixed seeds and
restore training RNG afterwards. `reload_check.json` checks an in-place delta
roundtrip; a fresh CLI process must additionally verify independent base+delta
loading. Do not call the in-place check proof of a standalone full-model export.

The Isaac entrypoint reuses ACT/SmolVLA action clipping, lockstep timing,
particle metrics, scene generation and video recording. All policies must be
reevaluated if the scene/sand/physics protocol changes. Random seeds are not
automatically independent held-out scenes. Record out-of-training-range scene
warnings and infrastructure failures separately from policy failures. Current
success stops after one scoop/unload, not repeated truck loading.

### Fixed-input precision diagnostic

Run only on an idle GPU, using the isolated PI05 environment. This is a
standalone investigation: it does not change the trainer, controller, existing
checkpoints, or live model weights.

```bash
"$PI05_PYTHON" ExcavatorVLA-vlm/scripts/diagnose_pi05.py \
  --checkpoint "$CHECKPOINT" --dataset data/export --episode 1 \
  --frames 0,3,8,20,30 --times 1.0,0.5,0.1 --gpu 1 \
  --output outputs/analysis/pi05_precision_<unique-name>

"$PI05_PYTHON" -m unittest discover -s ExcavatorVLA-vlm/tests \
  -p 'test_pi05*.py' -v
```

The selected episode must be an actual training episode. After verifying the
dataset fingerprint and loading base plus delta strictly, this compares:

- Training/inference preprocessing of the same recorded observation.
- Full training-style and KV-cached inference vector fields at identical
  observation, padded noise, normalized noisy action and flow time. Train/eval
  mode and CUDA BF16 autocast are varied separately; module-output traces help
  localize differences. Vector-field differences have normalized flow units.
- Actual ten-step sampled action chunks, with identical starting noise and
  autocast on/off, converted to physical rad/s before safety clipping.
- Disposable AdamW copies using one real, fixed, clipped training gradient and
  the checkpoint's saved optimizer moments, at saved and peak learning rates.
  Native mixed-dtype parameters are compared against FP32 parameter copies.

`report.json` records per-frame comparisons, parameter-group update fractions,
versions, source/checkpoint hashes and immutability checks; `arrays.npz` retains
noise, fields, target actions and sampled chunks. Outputs refuse overwrite.
Autocast off is **not** an all-FP32 model: original BF16 weights remain BF16.
The FP32 AdamW trial uses the same gradient and converted historical moments;
it does not reproduce a full FP32 training run or the historical accumulated
batch. These limited numerical checks alone do not establish the cause of a
closed-loop failure, learning success, or benchmark success rate. CPU helper
tests use synthetic tensors and must not be presented as real-model evidence.

## Acceptance gates

1. Assets: compatible environment, authorized local tokenizer, verified base.
2. Model: strict real-weight load, finite gradients and four-dimensional output.
3. Smoke: real exported observations/tasks, optimizer updates, save/reload and
   an independent offline CLI reload.
4. Resume: interrupted execution matches uninterrupted data/RNG progression.
5. Deployment: valid Isaac actions, complete traces, video and failure metrics.
6. Learning/task success: report separately after overfit/pilot and closed-loop
   diagnostics; finite smoke loss is not evidence of learned excavating.

Use an idle GPU and new output directories; all commands run from the parent
checkout using the isolated PI05 environment.

1. Pass the short real-data FP32 smoke, strict save/reload and independent CLI
   reload. Verify the provenance/manifest says all 430,098,464 trainable elements
   are FP32; confirm finite loss/gradients and FP32 AdamW moments. This gate says
   nothing about learning or simulator success.
2. Train a fresh 2,000-update run from the unchanged base on **export Episode 1**
   with micro-batch 1, accumulation 8, seed 1000, the existing LR schedule,
   action contract and normalization. Do not change the controller or action
   scale at the same time. Precision storage and matched inference autocast are
   the deliberate changes relative to the previous run.

   ```bash
   export BASE=/root/gpufree-data/ExcavatorVLA_new
   export PI05_PYTHON="$BASE/.venv-pi05/bin/python"
   export FP32_RUN="$BASE/outputs/train/pi05_fp32_overfit_20261021_01"

     --config ExcavatorVLA-vlm/configs/pi05/overfit.yaml \
     --gpus 1 --output "$FP32_RUN"
   ```

   The prior 2,000-step train-episode evaluation had first-action MAE 0.12301

   ```bash
   export PI05_CHECKPOINT="$FP32_RUN/checkpoints/002000/pretrained_model"

     --checkpoint "$PI05_CHECKPOINT" --dataset "$BASE/data/export" \
     --split train --episodes 1 --batch-size 1 \
     --output "$BASE/outputs/eval/pi05_fp32_overfit_ep1_20261021_01"
   ```

   still weak or not clearly better than the old run/zero baseline, inspect
